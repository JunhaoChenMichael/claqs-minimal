# SST-2 experiments — 2026-10-13

The full-training-set run reached **81.31% official validation accuracy** (macro F1 **81.27%**) after selecting epoch 1 of four. This report includes five smaller pilots, one full-data run, a historical snapshot evaluation, and separate GPU performance measurements. All new-run accuracies use the same labeled 872-example official SST-2 validation set; no hidden-label test file was evaluated. The old internal holdout score is identified separately as historical context.

## Accuracy comparison

| Run | Seed | Training rows | Best epoch / 4 | Validation accuracy | Macro F1 | Recorded training time |
|---|---:|---:|---:|---:|---:|---:|
| Control | 42 | 8,192 | 3 | 74.20% | 73.91% | 363.8 s |
| Padding mask | 42 | 8,192 | 2 | 76.72% | 76.71% | 363.1 s |
| Padding mask + regularization bundle | 42 | 8,192 | 2 | 76.61% | 76.57% | 365.9 s |
| Control | 43 | 8,192 | 3 | 72.71% | 72.69% | 368.1 s |
| Padding mask | 43 | 8,192 | 1 | 75.11% | 75.11% | 364.6 s |
| Full training set + padding mask | 42 | 67,349 | 1 | 81.31% | 81.27% | 375.4 s |

The mean best-epoch accuracy over the paired seeds is **73.45%** for control and **75.92%** for padding masking, a mean difference of **+2.47 percentage points**. The individual seed differences are 42: +2.52 points, 43: +2.41 points. These are descriptive results from two seeds, with no claim of statistical significance.

Within each seed, the control and masking pilots use exactly the same sampled training rows and training configuration, apart from padding handling. Seed 42 uses the dense implementation in both arms; the masked seed-43 arm uses the equivalent sparse implementation. Output and gradient equivalence are tested, although floating-point ordering can change training trajectories. Training subsets differ between seeds, so seed-to-seed variation includes subset sampling as well as initialization.

The regularization pilot bundles three changes relative to the masked seed-42 run: AdamW with weight decay 0.01, cosine scheduling, and head dropout 0.1. Its result cannot attribute gains or losses to any one component. The full-data result also changes training-set size and batch size, so it is not a controlled same-budget improvement over the pilots.

## Configuration and data protocol

All six new runs use 8 qubits, polynomial degree 3, two token-ansatz layers, one quantum feedforward layer, embedding dimension 128, a 64-token window, stride 64, one window per text, embedding dropout 0.1, learning rate 0.001, no label smoothing, and four epochs. The MLP classifier uses mean-logit aggregation. Vocabulary is built only from the actual training rows with minimum frequency 1 and a maximum size of 30,000. All current SST-2 training and validation texts fit in one 64-token window including EOS.

Control and masking pilots use Adam, zero weight decay, a constant learning rate and batch size 32. The full-data run uses masking with the sparse kernel, the same Adam settings and batch size 256. Best epochs are selected by official validation accuracy, so repeated use of this set for checkpoint selection and experiment choices introduces selection bias. These results are validation results, not an independent estimate of test performance.

Run configurations, data file hashes, hashes of pilot subset indices, epoch histories, confusion matrices, timing and parameter counts are preserved in [the JSON report](sst2_20261013.json). Datasets, individual text examples, checkpoint weights and machine-specific paths are excluded.

## Historical snapshot

The historical snapshot previously labeled 91.65% on its internal random holdout scored **76.03% official validation accuracy** (663/872; macro F1 76.02%) when evaluated with its correct measurement mask, mean-logit aggregation and legacy feedforward layout. Evaluation took 11.05 seconds. Every learned parameter matched; only transient TorchQuantum device-state buffers were ignored.

The snapshot lacks a saved vocabulary or complete configuration. Vocabulary was reconstructed from the current full ordered training parquet with the recorded tokenizer and frequency settings; its 13,819 entries match the embedding shape, but historical vocabulary provenance cannot be proven. It also used a larger architecture and a different training protocol, so its score is context rather than a same-budget baseline.

A separate audit of the old seed-42 random holdout found 1,560 of 6,734 rows (23.17%) matched a training-partition text after normalization with the tokenizer. This overlap makes the internal holdout a poor substitute for official validation. The official validation split was kept unchanged; the same audit found two normalized-text overlaps with the full training set. Different distributions and incomplete historical provenance also matter; the entire accuracy gap cannot be assigned to duplication alone.

## GPU memory and throughput

At the same batch size of 32, sparse padding reduced measured peak allocated memory from **842.8 MiB** to **152.9 MiB**, an **81.9%** reduction. It did **not** improve step time: dense 333.6 ms versus sparse 343.1 ms, a speed ratio of **0.972×**. Maximum logit difference on the benchmark batch was 9.54e-07. The batch contained 313 real tokens out of 2048 positions.

The reduced memory allows larger batches. A separate sparse-kernel benchmark measured:

| Batch size | Forward + backward time | Examples / second | Peak allocated memory |
|---:|---:|---:|---:|
| 32 | 335.9 ms | 95.3 | 152.9 MiB |
| 64 | 331.8 ms | 192.9 | 290.3 MiB |
| 128 | 334.1 ms | 383.1 | 587.9 MiB |
| 256 | 335.9 ms | 762.2 | 1115.2 MiB |

Batch 256 provides **8.00×** the measured examples/second of batch 32. This is a throughput ratio for forward/backward work with different batch sizes, not a same-batch kernel speedup or an end-to-end training speedup.

Both benchmarks use real SST-2 examples and an NVIDIA RTX A5000, with dropout disabled, gradients enabled and synchronized CUDA timing. Each comparison holds its trained snapshot fixed. Dense versus sparse uses two warmup steps plus ten measured steps; batch scaling uses two warmup steps plus five measured steps. Neither includes optimizer updates, data-loader work or preprocessing. Peak allocated memory is PyTorch allocation, not whole-device reserved memory. Reported per-run times above are the trainer's recorded elapsed times and come from different concurrent GPU jobs; they are not a controlled performance benchmark.

## Verification and next experiments

The local regression suite passed **11 tests**, including hidden-label rejection, validation-file identity checks, self-contained checkpoint loading, explicit feedforward parameter allocation and sparse/dense forward/gradient equivalence. Every new run completed four epochs and evaluated all 872 official validation rows; paired pilot subset equality was checked from the saved indices. The full-data checkpoint was independently reloaded and evaluated: accuracy, confusion matrix, macro F1 and sample count match its saved best-epoch result exactly. Its checkpoint SHA-256 and validation-file hash are recorded in the JSON report.

Next, repeat the full-data configuration across additional seeds, preserve a fixed validation-selection protocol, and separate the optimizer, schedule and head-dropout changes into individual ablations. A held-out labeled test or benchmark submission is required for a final test claim. These experiments do not establish parity with the paper's reported results.
